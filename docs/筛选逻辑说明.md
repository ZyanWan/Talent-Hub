# 简历筛选逻辑说明

> 本文说明 Talent Hub 简历筛选（初筛）的整体逻辑：系统如何理解岗位、如何给候选人分档、凭什么做出判断，以及每个判断如何被程序层层校验。
> 读者可以是两类人：**HR 用户**（不需要编程背景）和 **AI / 开发者**（需要可对照代码的准确口径）。正文用业务语言讲述，程序细节集中在「九、程序实现地图」并配有代码位置。
> 事实来源为当前代码实现；如需确认字段、状态机或数据流细节，参见文末相关文件清单与 [SOURCE_MAP.md](../SOURCE_MAP.md#6-简历筛选端到端数据流)。

---

## 一、这个筛选解决什么问题

简历初筛要同时面对三个难题：

1. **量大**：几十上百份简历，逐份翻完很费力，赶时间就容易凭感觉下结论。
2. **尺度不一**：同一个人，不同时间、不同人看，判断可能不一样；别人问"为什么留他/刷他"时，说不清依据。
3. **判断难复核**：想看当初为什么下这个结论，只能整份重读一遍。

Talent Hub 的筛选逻辑围绕一条主线设计：**把岗位标准翻译成机器可执行的检查清单，让每份简历按同一套清单打分分档，并且每一个判断都能指回简历原文**。它的产出不是"一个分数"，而是三层东西：

- 一个结论档位：**A 优先约面 / B 电话确认 / C 不推进**；
- 一份证据：这个结论是基于简历里的哪些事实，每一条都能回溯到原文；
- 一个行动建议：约面，还是先打一个电话确认某个关键事实，还是暂不推进。

## 二、一次筛选怎么跑完（用户视角全流程）

一次完整的简历筛选分两个阶段，**必须先有岗位标准，才开始评简历**。这样保证所有简历用的是同一把尺子。

```text
阶段一（定尺子）
  上传 JD → 系统自动生成《筛选标准》 → HR 校准、修改、确认
            │
            ▼（确认后才放行）
阶段二（量简历）
  上传一批简历 → 系统逐份评估 → 出结果（名单 + 证据 + 电话问题）
            │
            ▼
  Excel 评估表 + （可选）飞书推送
```

用户操作上对应这些步骤：

1. 在「新建」中创建**简历筛选**任务，填入标题；
2. 在任务页**上传岗位 JD**，并（可同时）**拖入一批简历**，点「开始筛选」；
3. 系统先解析 JD 并生成《岗位筛选标准》（Markdown），任务进入「等待校准」——**此时尚未评估任何简历**；
4. 打开标准页面**校对修改**：岗位本质、核心对象、业务场景、硬性门槛、A/B/C 规则等都可编辑，改完再点开始（此时若已上传简历，系统才开始逐份评估）；
5. 全部完成后进入结果页：可下载 Excel、可横向对比、可追加简历或修改标准后重筛、可推送飞书。

流程本身是**可续跑**的：评估途中关闭应用，下次重新发起会复用已保存的成功结果，只处理未完成的部分；跑完后还可以**追加简历**（只评新增的）或**修改标准后全量重筛**。

> 一次评估中每份简历只调用一次模型、之后不再二次复核，结果经原文证据校验后直接输出；拿不准的候选人被标记出来，由 HR 校对时自行判断。

## 三、岗位先被翻译成一份「筛选标准」

系统不拿 JD 原文直接去比对简历，而是先把 JD 提炼成一份结构化的检查清单。HR 在这份清单上校准，等于把用人口径"写"给系统。

清单包含以下部分（括号内是它在问什么）：

| 标准项 | 业务含义（在问什么） |
| --- | --- |
| 岗位本质 / 核心产出 | 这个岗位到底在解决什么问题，产出是什么 |
| 核心对象 | 候选人服务、处理、负责的对象：产品、客户、系统、渠道、物料、人群、区域……对象不对，动作再像也不算数 |
| 业务场景 | 候选人处在什么行业链路、产品形态、客户类型、交付模式里（垂直性） |
| 硬性门槛 | 必须满足的条件，如统招本科、某年限经验、限定行业。**只有 JD 用「必须/要求/至少/统招」这类必要措辞的才进这里** |
| A/B/C 条件 | 什么情况约面、什么情况电话确认、什么情况不推进 |
| 否决信号 / 相似错误画像 | 什么信号一票否决；哪些"看起来相关但其实不对"的人要警惕 |
| 加分信号 | 软性偏好，**只影响同档排序，不改变 A/B/C 结论** |

两条容易踩的边界，系统在生成标准时就用规则卡住：

- **期望 ≠ 门槛**：JD 里「熟悉/精通/具备/了解」是期望项，不放进硬性门槛；只有明确必要的措辞才算硬门槛。硬门槛条数过多，会把大量"其实不错"的人误伤成 C，也会让 B 无谓增多。
- **偏好 ≠ 必要条件**：JD 里「优先/优先考虑/加分项/欢迎/有相关经验者优先」只是偏好，进加分信号，不进场景、硬门槛或 A 条件。

## 四、每份简历怎么被判断

### 4.1 判断顺序

系统评一份简历，不是"扫一眼像不像"，而是按固定顺序走：

> 岗位本质 → **对象**对不对 → **场景**垂直不垂直 → 边界（JD 是否允许相邻行业迁移）→ **核心动作**做没做过 → **负责深度**（主导还是参与）→ **闭环** → **风险**（稳定性、层级、薪资等）→ 结论

顺序本身有意义：**先确认对象和场景，再看动作和深度**。目的是防止"张冠李戴"——做过相似的岗位名、但在完全不同的对象和场景上，不能按核心匹配算。

### 4.2 八个证据维度

系统把判断拆成八个维度。前四个是**核心维度**，直接决定 A 是否能成立；后四个是**辅助维度**，补充信息、用于细化风险与排序。

| 维度 | 业务含义（系统在看什么） | 是否核心 |
| --- | --- | --- |
| 对象 | 候选人实际处理的对象是否与岗位一致 | 核心 |
| 场景垂直性 | 行业链路 / 产品形态 / 客户类型是否与岗位垂直 | 核心 |
| 核心动作 | 是否做过岗位真正需要的动作（而非相邻、支持性动作） | 核心 |
| 负责深度 | 是主导、独立负责，还是协同、参与、支持 | 核心 |
| 闭环 | 是否有"发现问题→推动解决→形成结果"的证据 | 辅助 |
| 工具 / 系统 / 证书 | 是否用岗位相关工具解决过关键流程问题 | 辅助 |
| 规模 / 结果 | 是否有金额、数量、转化率、交付率、周期等结果数据 | 辅助 |
| 稳定性 | 工作时长、跳变、职业连续性 | 辅助 |

每个维度有一个**四档状态**：匹配 / 待确认 / 不匹配 / 未体现。

### 4.3 三条最重要的认知

判断贯穿始终的几条规则，直接影响你会看到什么结果：

1. **简历没写 ≠ 不匹配。** 候选人没写"用户增长"四个字，不代表没做过。系统允许基于完整经历做高概率推断——例如教育时间线连续完整的本科可推断为全日制；连续工作经历可推断年限；职责里包含需求、方案、推进、交付，可推断闭环能力。**推断必须有简历上下文支撑，编造是另一回事，绝对禁止。**
2. **软性缺口不降级。** 缺证书、缺工具名、缺结果数字，只写进备注，不因此把 A 打成 B。
3. **关键词本身不算证据。** 光写"负责、统筹、管理、全流程"而没有具体对象和动作，系统会往"空洞描述"方向判，而不是直接认作匹配。

## 五、结论三档：A / B / C 到底是什么

| 档位 | 含义 | 下一步 | 给 HR 的话 |
| --- | --- | --- | --- |
| **A 优先约面** | 四个核心维度都有指向原文的证据，硬性门槛全部满足，本质能力（需求洞察、方案设计、推动落地、结果负责）证据充分 | 直接约面试 | 前提是证据经得起原文核对；系统宁可让不够格的 B 去电话确认，也不让证据不足的人混进 A |
| **B 电话确认** | 存在**关键事实二义**：A 和 C 两种解读都说得通，且问一句电话就能直接改变推进决定 | 按附带的电话问题打电话核实 | B 是"定向核实"，不是模糊备选池；系统会为 B 生成针对具体二义点的电话问题 |
| **C 不推进** | 核心对象 / 场景 / 动作明确不符，或简历空洞无可核实经历，或硬性门槛不满足 | 暂不推进 | 系统会给出具体原因，HR 可复核 |

两个最容易误解的点：

- **什么样的简历才进 B？** 只有一种情况：**关键事实二义**——比如 JD 要求做某类产品，简历描述模糊到"A 和 C 两种解读都成立"。仅仅因为"简历写得太简略""没写某个关键词""缺证书"而进的，不算 B，系统按规则会直接判 A（可由经历推断）或 C（明确不符），不往 B 堆。
- **什么时候直接 C？** 三个来源：核心维度有**有原文依据的明确不匹配**；简历是**空洞描述**（四个核心维度全部无支撑、全文没有具体产品名 / 系统名 / 数字 / 流程细节）；**硬性门槛明确不满足**。

## 六、机器怎么兜底：三层校验，防止 AI 乱说

模型输出的结论不直接采用。程序对每个判断做三道校验，这是筛选逻辑里"算法"最核心的部分：

### 6.1 第一层：原文证据校验（引文必须指回简历）

判断 A/B/C 所用的"匹配 / 不匹配"必须能在简历原文里找到支撑，校验方式两种：

- **引文逐字核对**：模型给出的 quote 必须是简历原文的连续片段（去掉空白后比对）；
- **事实锚点兜底**：没有逐字引文时，维度摘要必须与原文共享具体事实——含 4 个及以上连续字符的片段、4 位以上的数字（如年份、金额）、或与原文共享足够多的中文词对（阈值见程序实现地图）。

找不到任何原文支撑的"匹配 / 不匹配"，一律**打回为「待确认」**，并写入证据校验提示。这一步专门拦截两类问题：AI 编造不存在的经历，以及用"负责、项目、运营"这类通用词凑出来的假支撑。

### 6.2 第二层：证据守卫（apply_evidence_guard）

打完证据校验后，按档位执行强制规则，方向**只降不升**：

| 模型说了什么 | 守卫发现什么 | 程序怎么改 |
| --- | --- | --- |
| A | 核心维度有「待确认」（原文支撑不住）或支撑匹配不足 | A 降为 B，附 blocker「A 类关键证据不足」 |
| B | 存在有原文支持的核心维度「不匹配」 | B 改判 C |
| B | 没有任何经过原文校验的核心正向匹配 | B 改判 C |
| B | 没有附带任何电话问题 | 自动补一个通用确认问题 |
| 非 B | 携带了电话问题 | 清空问题（C 不进电话确认流程） |

### 6.3 第三层：硬性门槛守卫（apply_hard_gate_guard）

硬性门槛逐条由模型判定 `met / unmet / unknown`，再经程序复核：

- **met / unmet 也要有原文支撑**，支撑不住的降为 unknown；
- 标准里的门槛模型没判 → 程序按 unknown 补齐（防止模型漏判导致硬门槛失守）；
- 任一 **unmet** → 无论模型说什么，**强制 C**，清空电话问题；
- 存在 **unknown** → A 不得成立（降为 B），并为未知门槛生成高优先级核实电话问题（至多 2 条）；**C 类不生成**任何核实问题。

### 6.4 为什么设计成"只降不升"

B 永远不能被重新提为 A，方向只有 A→B→C。背后的产品原则：**不确定的时候往保守走，宁可让 HR 打一个电话确认，也不冒险把没核实的人直接推去面试。** 三道校验全部落在代码里强制执行，不依赖模型每次自觉。

### 6.5 电话问题长什么样

B 类的产出是"打给这个人要问什么"。系统约束这些问题必须：

- 针对具体二义点（对象、环节、决策点），是**鉴别式提问**——让没做过的人无法泛泛作答；
- B 类问题不超过 3 个，至少 1 个高优先级；
- 问的内容不是简历已写明或可合理推断的信息；
- 优先级分层：高＝必须电话确认；中＝可用邮件 / 问卷核实；低＝备选池，不要求立即处理。

## 七、结果怎么排序和交付

### 7.1 排序

全部候选人按三层排：**先按结论分大组**（A 在前，B 居中，C 在后）→ **组内按证据充分度**（高 / 中 / 低）→ **再按证据强度**（八个维度加权打分：核心维度权重为普通维度的两倍，匹配 +3 / 待确认 +1 / 未体现 0 / 不匹配 −3，再减去风险条数）→ 最后按姓名。加分信号不改变 A/B/C 结论，也不进入这份程序排序。**推荐名单只收录 A 类。**（在结果页对选中候选人做「横向对比」时，由模型按岗位标准与各维度摘要重新排出约面顺序，是另一套 AI 排序，与表格的默认顺序互相独立。）

### 7.2 Excel 评估表（五张工作表）

| 工作表 | 内容 |
| --- | --- |
| 候选人总表 | 推荐顺序、结论、一句话判定、核心优势、关键风险、下一步动作、证据校验提示、硬性门槛判定、来源文件 |
| 证据匹配表 | 每个候选人在八个维度上的状态、摘要、原文引文、位置 |
| 电话确认问题 | 每位 B 类候选人的确认焦点与电话问题 |
| 筛选标准 | 本次使用的岗位标准（本质、硬门槛、A/B/C 规则、否决信号、加分信号） |
| 推荐名单（仅 A 类） | 可直接用于安排面试的名单与联系方式 |

Excel 生成后会做程序校验，校验通过才作为正式产物交付。

### 7.3 飞书推送（可选）

任务完成时推一条总览：本轮提交 / 成功 / 失败人数、A/B/C 分布，以及最多 5 位 A/B 候选人的姓名、结论和一句话判定。追加简历只推送新增结果；全部为 C 时只显示统计并提示当前没有建议优先处理的候选人。外发内容会隐藏手机号、座机号和邮箱。

## 八、边界：系统不做什么（HR 必读）

- 系统是**招聘辅助，不是录用决策**。AI 结果仅用于辅助判断，HR 与用人部门保留最终判断权。
- 关键岗位、校招、稀缺人才及**高风险淘汰结果**应保留人工复核。
- 准确性取决于 JD 清晰度、简历可解析质量、模型能力与用人口径；系统通过证据校验降低"无依据判断"的风险，但**不能承诺零误判**。
- 你会在总表里看到「证据校验提示」列——它专门列出程序发现"证据撑不住判定"的地方，是 HR 复核时**最该先看**的一列。
- 拿不准时系统的默认动作是**降档而不是硬给结论**。若某个结果你觉得意外，先看证据与原文引文，再判断是简历写法问题还是需要电话核实。

## 九、程序实现地图（AI / 开发者视角）

> 面向要改动或排查筛选逻辑的读者。业务口径见上文，本节给代码事实。

### 9.1 主流程（两阶段）

- 阶段一 `_prepare`（生成标准）：解析 JD → `criteria_system_prompt / criteria_user_prompt` → 模型输出 `ScreeningCriteria` → 落盘 `筛选标准.json` 与 Markdown → 任务转「等待校准」。参见 [pipeline.py](../app/pipeline.py) `_prepare`。
- 阶段二 `_run` / `_evaluate_one`：读标准 → 对每份简历并行 `_evaluate_one`：解析 → `evaluation_system_prompt / evaluation_user_prompt` → 模型输出 `CandidateEvaluation` → **`apply_evidence_guard`** → **`apply_hard_gate_guard`** → 原子落盘。业务上每份简历只做一次独立评估、不做二次复核；模型传输错误最多重试 2 次，输出结构校验失败时携带错误信息重发一次请求，二者都不构成第二次独立评估。参见 [pipeline.py](../app/pipeline.py) `_evaluate_one`、`_run`。
- 排序：`CONCLUSION_ORDER` → `EVIDENCE_ORDER` → `-evidence_strength` → 姓名；`evidence_strength` 对 8 维度加权（核心 ×2、其余 ×1；匹配 3 / 待确认 1 / 未体现 0 / 不匹配 −3）再减去 blocker 数。推荐名单仅取 A。参见 `evidence_strength`、`workbook_payload`。

### 9.2 判定数据结构（models.py）

- `ScreeningCriteria`：essence / core_outputs / target_objects / required_scenarios / allowed_adjacent / rejected_adjacent / hard_requirements / a_conditions / b_conditions / c_conditions / negative_signals / similar_wrong_profiles / bonus_signals 等。
- `CandidateEvaluation`：conclusion（`A优先约面 | B电话确认 | C不推进`）、evidence_level（高 / 中 / 低）、evidence（8 维）、hard_gate（逐条 met / unmet / unknown）、phone_questions、blockers、guard_warnings。
- `EvidenceDimension.status`：`匹配 | 待确认 | 不匹配 | 未体现`。`CORE_DIMENSIONS = {object_match, scenario_match, core_actions, ownership_depth}`。

### 9.3 事实锚点三通道（`_has_text_anchor`）

`text` 与规范化简历原文满足任一即视为有锚点：

1. 含连续 ≥ `min_chars`（默认 4）个字符且命中原文的片段；
2. 含 4 位以上数字且该数字出现在原文（时间线锚点，如 "2016"）；
3. 与原文共享 ≥ `min_bigrams` 个含汉字二元组。**证据守卫对维度判定使用 `min_bigrams=6`**（拦截仅凭通用词转述的判定）；**硬性门槛注记保留默认 4**（其推断以教育时间线等常规路径为主）。

### 9.4 守卫规则（行为与代码一致）

`apply_evidence_guard`：遍历 8 维，状态为「匹配 / 不匹配」时校验 `quote_valid = 规范化 quote ∈ 原文` 或 `_has_text_anchor(summary, min_bigrams=6)`；两者皆无 → 置「待确认」、清 location、核心维度记入 invalid_core、写 guard_warnings。quote 无效但摘要锚点有效 → 清 quote 保留判定并告警。之后规则改判：

- 模型结论 A 且（invalid_core > 0 或 supported_matches < 3 或任一核心维度 ≠ 匹配）→ 降 B；
- 结论 B 且存在有原文支持的核心「不匹配」→ 改 C；
- 结论 B 且 supported_core_matches == 0 → 改 C；
- 结论 B 且无电话问题 → 补 1 个通用高优先级问题；结论非 B → 清空电话问题。

`apply_hard_gate_guard`：对 `hard_requirements` 逐条取 verdict；缺失按 unknown 补齐并告警；met / unmet 无锚点 → 降 unknown。任一 unmet → 强制 C 并清空问题；存在 unknown → A 降 B；B 为 unknown 门槛生成高优先级核实问题（至多 2 条：第一条 `硬性条件核实-<id>`，其余合并 `硬性条件核实-其他`）；C 不生成核实问题。

### 9.5 提示词中的硬约束（与守卫互相咬合）

评估提示词 `evaluation_user_prompt` 内置约束：全部硬门槛 met 才可判 A；unknown 不得判 A（应 B 并生成核实问题）；unmet 直接 C；四个核心维度都须有「匹配」证据，可由完整经历高概率推断的维度应判「匹配」并写明推断依据，不得因没写关键词判「未体现」；B 的唯一准入是「关键事实二义」；C 不生成电话问题；电话问题须为鉴别式提问且 B 类 ≤ 3 个。标准生成提示词 `criteria_user_prompt` 内置硬门槛分级与偏好剥离规则（见第三节）。历史纠偏规则与通用证据规则分别由 [gotchas.md](../app/resources/references/gotchas.md)、[evidence-rules.md](../app/resources/references/evidence-rules.md) 注入提示词。
