# 历史侧栏操作与当前工作区状态一致性

状态：`[CLOSED]`

## 问题类型

历史侧栏的删除、归档、恢复与任务切换完成后，前端未把服务端结果统一提交到当前工作区，也缺少「最后一次用户选择生效」的守卫，导致主区域、当前任务、本地恢复键与服务端记录可能分别停留在不同记录或不同版本。

## 表现

### 表现一：删除、归档、恢复未同步当前工作区

- `HistoryDrawer` 的删除事件传到 `App`，但应用只处理电话任务，当前简历任务删除后仍保留 `state.currentJob` 和 `talentHub.lastJob`。
- 归档与恢复接口返回包含 `archived_at` 的最新任务摘要，`changeArchiveState()` 丢弃返回值并只刷新侧栏。
- 后端禁止对归档任务追加材料，主区域中过期的 `archived_at` 会让前端继续展示实际不可用的操作。

### 表现二：删除当前电话记录后主区域未重置

- 删除请求成功后侧栏列表刷新并移除记录，但主区域继续显示被删除任务，后续刷新请求会提示「任务不存在」。
- `HistoryDrawer.confirmDelete()` 成功路径只关闭确认框、刷新列表并显示提示，没有向应用层传递被删记录身份。
- 当前电话任务保存在 `state.currentCall`，恢复键保存在 `talentHub.lastCall`，电话工作区重置由 `App` 的 `phoneResetSignal` 驱动。

### 表现三：切换同为 results 视图的简历任务不刷新

- 已完成的筛选任务 A 和任务 B 都映射到 `results` 视图；`openJob()` 请求成功后把任务 B 写入普通全局对象 `state.currentJob`，再调用 `navigate("results")`。
- 当前视图已是 `results` 时，React 忽略值相同的 `setView("results")`，主内容区不重新渲染；抽屉关闭发生在任务 B 请求返回前，之后手动收起或展开侧栏才触发新渲染。
- 电话筛选页通过 `callOpenRequest` 加显式 `rerender()` 规避了依赖路由值变化的问题，简历任务未采用同样机制。

## 根因

前端把历史侧栏列表刷新和当前工作区提交分成互不关联的路径，任务加载缺少最新请求守卫；全局状态用普通对象保存，路由、状态对象与服务端记录可能各自停留在不同记录或版本。三个表现分别是「删除/归档/恢复未提交工作区」「删除未传递被删身份」「同视图切换缺少渲染通知」三个具体场景。

## 修复

- `HistoryDrawer` 使用 `HistoryMutation` 统一提交删除、归档和恢复结果；归档与恢复携带服务端最新摘要。
- `App` 按记录类型和当前 ID 提交变更：删除当前任务时重置对应工作区，归档与恢复时把摘要合并到完整任务；非当前任务只刷新侧栏。
- 简历任务打开使用 `jobOpenSeqRef`，电话任务打开使用 `callSelectSeqRef`；新选择、视图退出和工作区重置使早期请求失效。
- `openJob()` 成功写入 `state.currentJob` 并完成状态路由后，显式触发一次 App 渲染。
- 最新任务请求失败时清空对应当前任务与恢复键，主区域回到初始页。

## 修复后验证

- 历史抽屉验证覆盖 `HistoryMutation` 的归档与删除事件内容；电话删除单元测试断言删除当前任务后 `state.currentCall` 为 `null`。
- 简历集成验证覆盖当前任务归档/恢复、删除、快速切换乱序和最新请求失败；电话集成验证覆盖同样场景。
- 回归用例覆盖 `results` 到 `results` 的历史任务切换，不依赖再次收起或展开侧栏。
- 全量前端单元测试、TypeScript 类型检查和生产构建均通过。
