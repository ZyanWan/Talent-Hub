# [CLOSED] 历史记录与当前工作区状态一致性

## 目标

侧栏删除、归档、恢复和任务切换完成后，主区域、当前任务、本地恢复键与服务端记录保持一致；异步响应只允许最后一次用户选择生效。

## 观察

- `HistoryDrawer` 的删除事件传到 `App`，但应用只处理电话任务，当前简历任务删除后仍保留 `state.currentJob` 和 `talentHub.lastJob`。
- 归档与恢复接口返回包含 `archived_at` 的最新任务摘要，`changeArchiveState()` 丢弃返回值并只刷新侧栏。
- 简历 `openJob()` 和电话 `selectCall()` 都无请求身份校验，先发出的迟到响应可以覆盖后一次选择。
- `selectCall()` 的最新请求失败时只清除 `talentHub.lastCall`，旧 `state.currentCall` 和主区域保持不变。
- 后端禁止对归档任务追加材料，因此主区域中的过期 `archived_at` 会让前端继续展示实际不可用的操作。

## 假设

### H1：历史记录变更缺少统一的工作区提交边界（根假设）

- 支持：删除、归档、恢复分别刷新侧栏，但没有统一携带服务端结果同步当前工作区。
- 冲突：暂无。
- 验证：沿三条成功路径检查是否存在统一回调及当前 ID 匹配逻辑；结果为仅电话删除具备局部处理。

### H2：任务切换缺少“最后一次意图生效”约束（根假设）

- 支持：两个任务加载函数都在请求完成后无条件写全局当前任务。
- 冲突：轮询回调已有 ID 校验，但历史任务初次加载不走轮询提交逻辑。
- 验证：检查加载函数是否使用请求序号、AbortController 或目标 ID 校验；结果均不存在。

### H3：问题来自后端返回缺少归档状态

- 支持：主区域不知道归档结果。
- 冲突：`public_job_summary()` 与 `public_call_summary()` 都返回 `archived_at`。
- 验证：检查两个归档 API 的响应构造；H3 排除。

## 根因

前端把历史侧栏列表刷新和当前工作区提交分成了互不关联的路径，同时任务加载没有最新请求守卫，导致服务端状态、全局普通对象和 React 渲染通知可能各自停留在不同记录或不同版本。

## 修复

- `HistoryDrawer` 使用 `HistoryMutation` 统一提交删除、归档和恢复结果；归档与恢复携带服务端最新摘要。
- `App` 按记录类型和当前 ID 提交变更：删除当前任务时重置对应工作区，归档与恢复时把摘要合并到完整任务；非当前任务只刷新侧栏。
- 简历任务打开使用 `jobOpenSeqRef`，电话任务打开使用 `callSelectSeqRef`；新选择、视图退出和工作区重置使早期请求失效。
- 最新任务请求失败时清空对应当前任务与恢复键，主区域回到初始页。

## 修复后验证

- 历史抽屉验证覆盖 `HistoryMutation` 的归档与删除事件内容。
- 简历集成验证覆盖当前任务归档/恢复、删除、快速切换乱序和最新请求失败。
- 电话集成验证覆盖当前任务归档/恢复、删除、快速切换乱序和最新请求失败。
- 全量前端单元测试、TypeScript 类型检查和生产构建均通过。
